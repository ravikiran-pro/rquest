# Attributes, basic forms and real variants — design contract

Three layers. The catalogue knows everything; a shop fills the least.

```
catalog.attribute_definitions   every attribute once: type, unit, values, sources
catalog.attribute_sets          per sub-category (shop_type node): level, owner, variant axis,
                                basic-form flag, filterable
public.sub_categories           form_schema = the BASIC form (2–5 fields, generated)
                                variant_axes = ordered axis keys (generated)
public.shop_form_overrides      existing flow + enabled_attributes: extra attribute keys an
                                admin/owner switches on for that store
```

Source of truth for the data: `catalog/attributes/build/` (generated by the merge step from
`research/*.json`). Never hand-edit generated files; fix the research or the merge.

## 1. Catalogue schema (`catalog` schema, migration 4, `catalog/db/schema.js`)

- `catalog.attribute_definitions` — `key` PK (`^[a-z][a-z0-9_]{0,39}$`), `label`, `type`
  (`text|textarea|number|boolean|date|enum|multi_enum|measure`), `unit_family`,
  `default_unit`, `values` jsonb array, `open_values` bool, `description`, `shopify_handle`,
  `ondc_attribute`, `sources` jsonb array, + loader tracking columns.
- `catalog.attribute_sets` — `node_id` → `taxonomy_nodes(id)` (`shop_type:<sub key>`),
  `attribute_key` → `attribute_definitions(key)`, `level`
  (`statutory|required|recommended|optional`), `owner` (`catalog|store`), `per_variant`,
  `filterable`, `axis_order` (null = not a variant axis, else 1..n), `in_basic_form`,
  `sort_order`, `note`; PK `(node_id, attribute_key)`.
- `catalog.item_families` — a product sold in several variants. `id` text PK
  (`fam:<sha>`), `name`, `brand_key`, `taxonomy_node_id`, `variant_axes` jsonb array of
  attribute keys, `attributes` jsonb (shared facts).
- `catalog.items` gains `family_id` → `item_families(id)` (nullable) and `variant_values`
  jsonb object (`{"size":"M","colour":"Navy"}`; keys ⊆ family axes). One item = one SKU.
- `catalog.items_enriched` is recreated to also expose `family_id`, `variant_values`.
- Loader source `attribute-sets` reads `catalog/seeds/attributes/*.json` (built files).

## 2. App: basic forms

- `src/api/data/taxonomy.js` sub-category entries get `basic_fields` (keys) and
  `variant_axes` from the build; `taxonomy:sync` writes `sub_categories.form_schema` (basic
  form only; field definitions come from the dictionary export
  `src/api/data/attributeDictionary.json`) and `sub_categories.variant_axes`.
- Existing listing metadata is never deleted. A key that leaves the basic form is still
  stored; it shows again when the store enables it.

## 3. App: store-enabled attributes (extends shop_form_overrides)

Override document adds `enabled_attributes: ["fabric", "care_instructions", ...]` — keys
from that sub-category's attribute set (not variant axes). Resolved form = basic form +
enabled attributes (defs from the dictionary) + custom_fields, then the existing
hide/label/required overrides. Statutory store-owned attributes are always in the basic
form, so they cannot be disabled.

## 4. App: real variants

Tables (Sequelize migration in `src/api/migrations/`):

- `listing_variants`: `id` uuid PK, `listing_id` → `shop_listings(id)` ON DELETE CASCADE,
  `option_values` jsonb object (axis key → value), `sku` text null, `price` float not null,
  `mrp` float null, `stock_qty` int null, `low_stock_threshold` int null, `is_available`
  bool default true, `catalog_item_id` text null (the catalogue SKU), `img_url` text null,
  `position` int default 0, timestamps; unique `(listing_id, option_values)`.
- `shop_listings.variant_axes` jsonb default `[]` (ordered axis keys this listing uses;
  `[]` = simple listing, behaves exactly as today).
- `order_items.variant_id` → `listing_variants(id)` null, `variant_label` text null
  (snapshot, e.g. "M / Navy").

Rules:
- A listing with variants keeps `price` = lowest available variant price and
  `is_available` = any variant available (denormalised for search/sort; maintained by the
  write service, never sent by clients). Stock lives on variants when `variant_axes` is
  non-empty (listing `stock_mode` applies to all its variants).
- Axis keys must come from the sub-category's `variant_axes` (or the store's enabled
  attributes when the attribute is marked `per_variant`); values for enum axes must be in
  the dictionary values unless `open_values`.
- Orders: the server always takes price from the variant, deducts/restocks variant stock
  (existing `stock_deducted` semantics), and rejects an order line for a listing with
  variants that has no `variant_id`.
- API: listing create/update accept `variant_axes` and `variants: [{ id?, option_values,
  price, mrp?, sku?, stock_qty?, low_stock_threshold?, is_available?, img_url? }]`
  (full replace semantics, matched by `id` or `option_values`); listing reads include
  `variant_axes` and `variants` sorted by `position`. Order create accepts `variant_id` per
  item. Cart line identity = `listing_id + variant_id`.
- UI: product editor shows a variant matrix (pick axis values → rows with price/MRP/stock);
  storefront/offering card shows option pickers; cart and order views show the variant
  label.
